# 0019: The graph's renderer indexes big graphs in slices

**Context.** Choosing the graph's Everything level (46,759 nodes and 141,218 links on desktop) froze the page (issue #3). Sigma's constructor indexes the whole graph in one synchronous call: reducers on every node and edge, normalisation, the label grid and every WebGL buffer, then a draw. On top of that, the year/selection effect ran a second full refresh as soon as it was registered. On an M-series Mac this made one 245 ms task, and about 1 s at 4× CPU slowdown. A worker can't help, because sigma's indexing writes to the WebGL buffers on the main thread. A progressive reveal (mount a subset, then stream the rest) still pays one full `process()` per added batch, and the last batch costs as much as the whole graph.

**Decision.** `atlas/src/graph/chunkedSigma.ts` subclasses Sigma. When the constructor's first full refresh covers more than 20,000 nodes and edges, the subclass runs the same work as `Sigma#refresh` and `Sigma#process` in 12 ms slices, yielding between them, and then draws once. Renders and refreshes asked for meanwhile wait, and a refresh request triggers one more sliced pass. Smaller graphs keep sigma's own path. GraphView wires its handlers once the first draw is done, and it no longer refreshes again when nothing has changed since the indexation began.

**Why.** It is the smallest change that removes the long task entirely. The Everything level now loads with no task over 50 ms, at desktop and phone sizes and at 4× slowdown, and paints sooner than before (median 347 ms after the click, down from 401 ms). Screenshots are pixel-identical. The cost is a copy of about 80 lines of sigma 3.0.3 internals. `atlas/package.json` pins sigma exactly, so re-check the copy against `Sigma#refresh` and `Sigma#process` before any upgrade.
